# 健壮性

软件应该*是*健壮的(处理坏输入、幂等),并且*感觉*健壮(即时、响应迅速、不脆弱)。两者都重要。

## 校验用户输入

程序任何接收用户数据的地方,迟早都会收到坏数据。在边界检查,快失败,错误信息要清晰。(参见 `errors.md`。)

## 响应 > 速度

<100ms 内输出点什么。网络请求前先打一行状态。用户永远不应该疑惑“这东西是不是挂了?”

```
$ myapp sync
正在连接 api.example.com...
正在获取 14 项...
  1/14 .............................. ok
  2/14 .............................. ok
  3/14 .............................. ok
  ...
同步完成: 14 项, 用时 3.2s。
```

## 长时间操作要显示进度

如果程序一段时间不输出,看起来就像挂了。旋转图标、进度条、动画元素,能让程序显得比实际更快 —— 也让用户知道工作还在继续。

`docker image pull` 演示了多个并行进度条如何提供关键的可观察性:


## 并行

- 并行进度报告比顺序难十倍。
- 用现成库:`tqdm`(Python)、`schollz/progressbar`(Go)、`node-progress`(Node)。它们原生支持多进度条,值得用。
- 并行工作的输出如果交错,容易让人迷惑 —— 选一个输出策略(每 worker 一行、聚合进度条、或每 worker 独立条),并坚持用。

## 超时

允许配置网络超时,并提供合理的默认值。永远挂起的 CLI 在网络不好时无法使用。

## 可恢复

如果程序因瞬时原因失败(网络断了、服务器返回 503),用户应该能按 `<up>` + `<enter>` 续上。从一开始就把幂等性做进去。

## crash-only

幂等性的更强版本。如果能避免清理、或把清理延后到下次运行,程序就能在失败或中断时立即退出。这让程序更健壮(没有清理到一半的状态)也更响应迅速。

含义:

- 写入应该是原子的(写入临时文件,然后改名)。
- 状态应该能从真值源重建(不依赖前次清理完成)。
- 下次运行应能检测并修复上次中断运行留下的任何部分状态。

(延伸阅读: *Crash-only software: More than meets the eye*。)

## 用户一定会滥用你的程序

做好准备。用户会:

- 把工具塞进脚本。
- 在糟糕的网络下使用。
- 同时运行多个实例。
- 在你没测试过的环境里跑(不同的 shell、诡异的终端、NFS 文件系统、没有 TTY 的容器)。
- (你知道 macOS 文件系统是大小写不敏感但保留大小写吗?)

为能想到的场景设计;对想不出的场景优雅失败。
