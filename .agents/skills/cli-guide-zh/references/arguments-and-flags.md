# 参数与选项

CLI 两种输入,以及让它们可预测的约定。

## 术语

- 参数(args) —— 位置参数。`cp foo bar` 是经典例子,顺序很重要。
- 选项(flags) —— 命名参数,带 `-`(单字母)或 `--`(完整名)前缀。可带可不带值(`--file foo.txt` 或 `--file=foo.txt`)。通常顺序不影响语义。

## 优先用选项而非参数

多一点输入量,但更清晰。也让接口面向未来 —— 当你需要新增输入时,参数会强迫你制造歧义或破坏既有行为。(引自 *12 Factor CLI Apps*。)

## 始终提供完整名称

`-h` 和 `--help` 都要。完整名在追求可读性的脚本中很有用。(引自 *GNU Coding Standards*。)

## 单字母选项只留给常用选项

别把短选项命名空间塞满。`-x` 一旦有含义,你就很难再收回。

## 同一目标的多个参数 —— 没问题

`rm file1 file2 file3` 工作,`rm *.txt` 也工作。glob 应该工作。

## 不同含义的两个以上参数 —— 通常是坏味道

例外是最常用的主操作,简洁值得背,比如 `cp <源> <目标>`。(引自 *12 Factor CLI Apps*。)

## 标准选项名

用其它工具已用的同名选项,让用户不用读 help 就能猜。

| 短      | 长                  | 含义                                            |
|--------|--------------------|-----------------------------------------------|
| `-a`   | `--all`            | 全部(如 `ps`、`fetchmail`)                          |
| `-d`   | `--debug`          | 显示调试输出                                       |
| `-f`   | `--force`          | 强制执行,即使有风险;也用于脚本里跳过确认(如 `rm -f`)        |
|        | `--json`           | 输出 JSON                                        |
| `-h`   | `--help`           | 帮助 —— 不要赋予它别的含义                            |
| `-n`   | `--dry-run`        | 描述会发生什么然后退出(如 `rsync`、`git add`)           |
|        | `--no-input`       | 禁用交互式提示(参见 `interactivity.md`)              |
| `-o`   | `--output`         | 输出文件(如 `sort`、`gcc`)                          |
| `-p`   | `--port`           | 端口(如 `psql`、`ssh`)                            |
| `-q`   | `--quiet`          | 减少输出                                          |
| `-u`   | `--user`           | 用户(如 `ps`、`ssh`)                              |
|        | `--version`        | 版本                                            |
| `-v`   | (verbose 或 version) | 经常被复用 —— 建议用 `-d` 表示 verbose 以避免混淆        |

## 默认值要照顾大多数用户

大多数用户不会主动找到并记住一个偏僻选项。如果 `ls` 是今天设计的,默认大概就是 `ls -lhF`。默认针对最常见情况优化;高级用户仍可翻选项。

## 缺参数时主动提示

如果用户漏了参数,交互式提示。但绝不强制交互 —— 始终提供选项/参数替代。`stdin` 不是 TTY 时跳过提示,要求通过选项/参数传入。

## 危险动作要二次确认

按影响半径分三档:

- 轻度 —— 小范围本地变更(如删除单个文件)。如果命令名已经明确(“delete”),通常不需要提示。用户运行 `myapp delete file.txt` 时已经知道自己在做什么。
- 中度 —— 较大本地变更(删除目录、批量编辑),或任何远程变更(删除远程资源)。提示确认,或提供 `--dry-run` 让人谨慎行事。
- 重度 —— 破坏性、难以回退(删除整个应用或服务器)。不只是提示 —— 让它难以被误触。考虑要求用户输入要删除对象的名字,同时支持 `--confirm="name-of-thing"` 以便脚本化。

留意隐性风险:把配置里的数字从 10 改成 1,可能隐式删除 9 个东西。这条路径算重度,即便“改一个配置值”听起来无害。

## 支持 `-` 表示 `stdin`/`stdout`

当输入或输出是文件时,接受 `-` 表示 `stdin` 或 `stdout`。让一个命令直接喂给另一个,无需临时文件:

```
$ curl https://example.com/something.tar.gz | tar xvf -
```

## 可选值允许 `none`

`ssh -F none` 表示不用任何配置文件。空字符串会有歧义(下一个位置参数是选项值还是真正的参数?)。用一个真实的词如 `none`。

## 让参数/选项/子命令顺序无关

用户会按 `↑` 加个选项再回车。两条都该工作:

```
$ mycmd --foo=1 subcmd
works

$ mycmd subcmd --foo=1
unknown flag: --foo
```

修第二条。

## 密钥不进选项

**密钥一旦进入命令行选项或环境变量,就会出现在进程列表和 shell 历史里,等于公开。**密钥只从文件或受保护存储读取。

- 选项值会泄漏到 `ps` 输出和 shell 历史。
- `--password-file` 或 `stdin` 是正确做法。
- `--password $(< file.txt)` 和 `--password` 一样有泄漏问题。不要用。

```
# 差: 密钥在选项里,在进程列表里,在 shell 历史里
$ myapp --password=hunter2

# 好: 密钥在文件里
$ myapp --password-file=./secret.txt

# 也好: 密钥走 stdin
$ cat ./secret.txt | myapp --password=-
```
