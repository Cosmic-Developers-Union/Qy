# 面向未来

任何软件的接口都不应未经漫长且有据可查的弃用流程就改变。子命令、参数、选项、配置文件、环境变量都是接口,你承诺了会保持它们工作。(语义化版本控制只能为这么多变更开脱;如果你每个月发一次大版本,那它就毫无意义。)

## 变更尽量叠加

不要对既有选项做破坏性修改,加一个新选项 —— 只要别把接口撑得太胀。

## 破坏性变更前先警告

终有一天你不得不破坏一个接口。在此之前,在程序内部先警告用户:

- 当他们传入你打算弃用的选项时,告诉他们这个选项要变了。
- 告诉他们今天就怎么迁到新用法。
- 如果可能,检测到他们已迁移后停止警告。

```
WARNING: --output-format=yaml 已弃用,将在 v3.0 移除。
         请改用 --format=yaml。你更新配置后,本警告会自动消失。
```

## 人读输出可以改

让接口好用的唯一办法就是迭代。如果人读输出也算接口,那就迭代不了。让用户在脚本里用 `--plain` 或 `--json` 固定输出。(参见 `output.md`。)

## 不要“万能兜底”子命令

省略最常用的子命令有时很诱人。比如你有一个 `run` 子命令,包装任意 shell 命令:

```
$ mycmd run echo "hello world"
```

你可能会让:如果 `mycmd` 的第一个参数不是已有子命令,就当作 `run`:

```
$ mycmd echo "hello world"
```

这有严重的副作用:你再也不能加一个叫 `echo` 的子命令 —— 或任何子命令 —— 而不冒着破坏既有用法的风险。如果有脚本在用 `mycmd echo`,用户升级到新版本后,这个脚本就会做出截然不同的事。

## 不要允许子命令的任意缩写

比如你的命令有 `install` 子命令。你想给用户省点输入,就允许任何无歧义的前缀 —— `mycmd ins`,甚至 `mycmd i` —— 都能当成 `mycmd install`。

这下你就被套牢了:你再也不能加任何以 `i` 开头的命令,因为脚本里有人假设 `i` 就是 `install`。

显式别名没问题。给用户省输入是好事。但别名要显式定义、稳定保留。

## 别埋定时炸弹

想象 20 年后。你的命令还能像今天这样工作吗?还是会因为某个外部依赖改了或不再维护而停止工作?

最可能在 20 年后不存在的服务器,是你现在正在维护的那个。

- 核心行为不要依赖外部服务,除非你也能提供一个降级方案。
- 不要在每次调用时阻塞式地打 Google Analytics。
- 不要内嵌会“打电话回家”检查新版本号之类逻辑。
